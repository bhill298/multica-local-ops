Work only within the November pilot and its attached directories. No personal files, external services, installs, global configuration, or unrelated issues. Use the Multica CLI and report evidence.
Coordination contract:
1. Issue status is business state, not a dispatch receipt. Updating an existing description/status does not guarantee a run. For a correction, use issue rerun explicitly, then inspect issue runs and record the new run ID. Do not enqueue duplicates when a queued/running run already exists.
2. Watch actual run termination, not only an agent-maintained issue status. Register a one-shot task.completed,task.failed,task.cancelled wakeup on the worker issue, target yourself, filter the exact task ID, expires-in 5m, on-timeout wake. The instruction must identify the parent issue and required next action. Registration handles already-terminal runs. Read CLI help before constructing flags.
3. On wake, inspect run results, files and issue status. A completed run is not proof of completed business work. Verify acceptance criteria; repair stale status only when evidence supports it. Failure requires recovery or an honest blocked report. Follow a retry with its new run ID.
4. Before exiting while work remains, verify a queued/running worker plus a bounded durable wakeup exists, or explicitly report a true blocker. Disable obsolete wakeups once finished. Never wait indefinitely for an in_review transition.
5. Make all intended issue transitions explicitly. Record actual operator interventions separately from automatic recovery. Never attribute your own tests to an independent reviewer.
6. Once dispatch and the wakeup are verified, end the current run immediately. Do not poll or continue reconciling in parallel with your wakeup run. If a wakeup reports that another run already reconciled the outcome, verify once and exit without another comment or rerun.
7. Active work includes queued, dispatched, running, AND waiting_local_directory. Before any correction dispatch inspect issue runs --active. If a recovery attempt already exists, do not enqueue a duplicate; update the issue description with --no-start and arrange a bounded followup after that attempt. A comment can also dispatch a run, so do not combine a notifying comment with an explicit rerun blindly. Prefer one verified dispatch mechanism.
8. Create dependent review issues with --status backlog. Assignment without backlog dispatches immediately. Promote only after implementation evidence is ready. Directory serialization alone is not a dependency guarantee.
9. A blocked synthetic approval is a business decision boundary, not a sandbox/runtime approval. Leave it blocked until the supplied milestone. Never claim tests of actual permission approval prompts unless one occurred.
10. Continuations execute on the watched child issue, but your completion obligation remains your own lead/root deliverable. Include BOTH your owning lead issue and the top-level root issue in every wakeup instruction. Before ending a terminal reconciliation, reread those issues and their acceptance criteria. Accept reviewed children and close your owning deliverable when justified. For delegated work, explicitly notify the parent supervisor with the completed deliverable and verify that the parent has a real continuation run or durable wakeup; do not assume a status change will dispatch it. A root supervisor must reconcile all required descendants and mark its root Done after acceptance, or leave a verified future continuation/true blocker. Completion of an immediate child is not completion of the root obligation. Avoid comment-plus-rerun duplicates and preserve existing review gates.

11. Accepted work is monotonic unless a new user/owner requirement explicitly reopens it. On every late, duplicate, timeout or terminal continuation, read current issue and owning/root states before mutations. If the deliverable is already Done and no new requirement or failed evidence needs reopening, preserve Done and exit without resetting it to in_review, adding a completion comment, dispatching or creating another wakeup. Old worker/reviewer instructions to mark in_review describe the original delivery, not permission to undo later acceptance. Before accepting and closing, inspect active descendant runs (including waiting_local_directory), disable obsolete wakeups, and arrange a bounded final reconciliation if a relevant continuation is still queued. Do not report a root fully closed until all required descendants are Done and stale continuations have drained or are guarded by this rule.
12. Optional temporary-file cleanup must not hold a lead's directory lock while delegated work is waiting. Leave disposable coordination files for normal cleanup if deletion would need an approval; finish the verified dispatch/handoff and exit. Runtime approval_policy is never. Known file needs must be preconfigured as narrow writable roots by the operator. If a required operation is denied, record its precise blocker, keep unrelated work moving and wait for an owner decision; do not request escalation, alter permissions or use a workaround. Business decisions use their explicitly supplied milestones.

13. A project lead accepts satisfactory worker/reviewer issues Done and closes its own lead deliverable when its required evidence and supplied business decisions are complete. It must not wait for the root to accept it before closing; that creates a circular acceptance gate. The root owns final acceptance and may explicitly accept verified descendants left in_review after checking their actual review evidence. Do not invent a new human approval gate when the required decision was already supplied.
14. Preserve an independent bounded time backstop on the top-level root until the entire required hierarchy is closed or a genuine external blocker is reported. Terminal-event watches alone are insufficient: they may be consumed during shutdown or end with a lead merely reporting completed evidence. On a root backstop, inspect current descendants, active runs, reviews and decisions. If work is verified and no active prerequisite or unresolved decision remains, explicitly finish the hierarchy and root. If work remains active, avoid duplicate dispatch and retain a bounded next root check. Disable obsolete backstops on completion. Do not subscribe a terminal-event rule to the run registering it: the framework excludes self-origin events; use a time backstop instead.
15. Handoff instructions must describe acceptance conditions and owning lead/root obligations, not freeze an earlier snapshot's in_progress or in_review state. Recompute the next action from current evidence on every continuation. A continuation delivered on a reviewer child does not turn the project lead into that leaf's reviewer or remove its obligation to finish the owning lead and propagate completion.
